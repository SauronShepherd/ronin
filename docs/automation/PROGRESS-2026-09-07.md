## Runtime contention qualification

Starting `main`: `e15ef2e7b75de49c3689fead76fd2d5703449865`.

The current canonical backlog and construction plan supersede the earlier CLI-first suggestion: #125 remains ahead of HTTP and CLI until the real runtime storage/artifact call sites have bounded-contention evidence.

This slice adds a real-SQLite/local-artifact integration qualification at the existing production async boundaries. It deliberately injects one slow SQLite status operation while proving a second executor worker can still renew the active Attempt lease, and separately injects one slow local-artifact write while proving verification of an existing artifact can still make progress. ## Shared execution boundary before HTTP

Starting `main`: `10835f4d338250822429a2747c7e9f3f3c1f8983`.

#125 now has real-adapter structural contention evidence, while its remaining HTTP p95 criterion cannot be completed before a supported HTTP runtime exists. Before opening that HTTP surface, #139 identifies a concrete dependency inversion: `studio_worker` imports shared HTTP-neutral application logic from the outer `studio_server` package.

This slice relocates the single `DurableExecutionService` implementation and `WorkerPollResult` to the new neutral `studio_execution` application package. `studio_server` re-exports the service for compatibility but no longer owns its implementation; `studio_worker.runtime` and `studio_worker.execution` import `studio_execution` directly. The executable architecture dependency matrix now forbids `studio_worker -> studio_server`, and a negative regression fixture proves such an import fails with `DEP001` while `studio_worker -> studio_execution` remains allowed.

The move preserves the same bounded `BoundedAsyncJobStore` composition, lease fencing, storage semantics and worker behavior. `studio_execution` is included in mypy and measured coverage, and no HTTP framework, SQLite adapter type, Docker type, cloud/provider type or duplicated service logic enters the shared package. The old `studio_server/durable_execution.py` implementation is removed.

## First real HTTP submit/status boundary

Starting `main`: `0468368ae2f424568c8a37f64edcc13d1d0dbc68`.

The remaining #125 HTTP p95 criteria require real server entry points, so the next coherent dependency-complete increment of #54 is intentionally narrow: only authenticated `POST /v1/jobs` and `GET /v1/jobs/{job_id}` over the already-neutral `DurableExecutionService`. This does not attempt events, evidence, cancellation, CLI, Compose or release work in parallel.

`studio_server.http` now provides a standard-library `ThreadingHTTPServer` adapter whose request threads marshal durable operations onto one dedicated asyncio loop. All synchronous `JobStore` work therefore remains behind the existing bounded `BoundedAsyncJobStore`; HTTP request threads never call SQLite directly. Static Authorization is mandatory and checked with constant-time comparison. Typed scope/grant semantics remain explicitly pending under #52 rather than being invented inside the HTTP adapter.

The HTTP adapter constructs the existing canonical `Job`/`Run` lifecycle objects, preserves `Job.parameters_json` as the worker's parameter-only payload, and hashes project + target + parameters for idempotency identity. SQLite remains the idempotency authority: replaying the same key and request returns the original Job, while reusing that key for different content returns the normalized `idempotency_conflict` error.

`api/openapi-v1.json` is the first version-controlled OpenAPI 3.1 contract for these two routes. A drift test requires the documented method/path set to equal the server's executable route set and requires the documented Job state enum to equal the existing `pyronin` enum. A real integration test uses a TCP socket, authenticated `pyronin.HTTPTransport`, `Ronin`, `DurableExecutionService`, and real `SqliteJobStore` to prove submit, status, idempotent replay, conflict, authentication, invalid request and not-found behavior through the public protocol boundary.

This slice advances #54 but does not satisfy it: list/events/evidence/cancel, typed scopes, complete route/OpenAPI coverage, compatibility/evolution policy and the full real-server SDK journey remain. It also does not yet satisfy #125: the new real entry points make its POST/GET p95 contention qualification possible, but no latency claim is made until exact measurement evidence exists.
