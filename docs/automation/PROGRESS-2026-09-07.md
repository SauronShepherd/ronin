## Runtime contention qualification

Starting `main`: `e15ef2e7b75de49c3689fead76fd2d5703449865`.

The current canonical backlog and construction plan supersede the earlier CLI-first suggestion: #125 remains ahead of HTTP and CLI until the real runtime storage/artifact call sites have bounded-contention evidence.

This slice adds a real-SQLite/local-artifact integration qualification at the existing production async boundaries. It deliberately injects one slow SQLite status operation while proving a second executor worker can still renew the active Attempt lease, and separately injects one slow local-artifact write while proving verification of an existing artifact can still make progress. It does not claim the frozen POST/GET p95 product budgets are satisfied because the HTTP server does not exist yet. #125 therefore remains open until its remaining final-call-site/budget criteria are evidenced; the new test closes the gap between service-level in-memory doubles and real SQLite/artifact adapters without weakening durability or admission bounds.

## Shared execution boundary before HTTP

Starting `main`: `10835f4d338250822429a2747c7e9f3f3c1f8983`.

#125 now has real-adapter structural contention evidence, while its remaining HTTP p95 criterion cannot be completed before a supported HTTP runtime exists. Before opening that HTTP surface, #139 identifies a concrete dependency inversion: `studio_worker` imports shared HTTP-neutral application logic from the outer `studio_server` package.

This slice relocates the single `DurableExecutionService` implementation and `WorkerPollResult` to the new neutral `studio_execution` application package. `studio_server` re-exports the service for compatibility but no longer owns its implementation; `studio_worker.runtime` and `studio_worker.execution` import `studio_execution` directly. The executable architecture dependency matrix now forbids `studio_worker -> studio_server`, and a negative regression fixture proves such an import fails with `DEP001` while `studio_worker -> studio_execution` remains allowed.

The move preserves the same bounded `BoundedAsyncJobStore` composition, lease fencing, storage semantics and worker behavior. `studio_execution` is included in mypy and measured coverage, and no HTTP framework, SQLite adapter type, Docker type, cloud/provider type or duplicated service logic enters the shared package. The old `studio_server/durable_execution.py` implementation is removed.

## First real HTTP submit/status boundary

Starting `main`: `0468368ae2f424568c8a37f64edcc13d1d0dbc68`.

The remaining #125 latency criteria require real server entry points. This #54 increment is therefore limited to authenticated `POST /v1/jobs` and `GET /v1/jobs/{job_id}` over the existing neutral `DurableExecutionService`; events, evidence, cancellation, CLI, Compose and release work remain outside this slice.

`studio_server.http` is a standard-library outer adapter. Request threads marshal durable calls onto one dedicated asyncio loop, and synchronous persistence remains behind the existing bounded async storage wrapper. Static request authentication is required and comparison is constant-time. Typed grants remain pending under #52.

The adapter constructs existing canonical `Job` and `Run` values and preserves the worker parameter payload shape. Replay identity remains delegated to the existing SQLite storage contract using a digest of project, target and parameters; identical replay returns the original Job while conflicting content produces the normalized conflict response.

`api/openapi-v1.json` versions exactly the two implemented routes. Contract tests tie its route set and Job-state enum to the executable server and existing `pyronin` SDK. The integration qualification uses a real TCP socket, real SQLite, the real durable service and `pyronin` to prove submit, status, replay, conflict, authentication, invalid-request and not-found behavior.

This advances #54 without completing it. Additional routes, typed grants, full compatibility policy and the complete server-backed SDK journey remain. #125 also remains open: these entry points now make its latency qualification possible, but this slice makes no performance claim.
