## Worker runtime contention qualification

Starting `main`: `b9fcc7450712fff17c4f08cee4a8cd3adf9a438f`.

The remaining #125 worker-side criteria are now exercised through `LocalWorkerRuntime.run_once`, the production v0.1 worker composition boundary. The qualification keeps the production defaults intact: 30-second lease, 10-second heartbeat cadence, bounded JobStore executor 4 workers / 8 in flight, and bounded artifact executor 2 workers / 4 in flight.

One scenario blocks a real SQLite status call while the worker is executing and proves, from the durable `attempts.heartbeat_at` and `lease_expires_at` rows, that the heartbeat task renews the lease. The same running Attempt then blocks a real local artifact checkpoint write and proves a later durable heartbeat and lease extension still occur before the write is released. A second scenario leaves one persisted cell under an expired Attempt, reclaims the same Run through a replacement `LocalWorkerRuntime`, blocks the real artifact verification used for resume, proves the replacement Attempt renews its lease during that contention, then verifies exactly one cell is reused and the remaining four execute.

The blocking fixtures only delay selected synchronous adapter calls; the runtime, bounded async facades, SQLite lifecycle/fencing, artifact implementation and worker entry points are production code. Wall-clock waiting exists only to permit the unchanged 10-second heartbeat cadence to fire; the assertions use durable lease state rather than elapsed-time thresholds. Existing real-Docker crash/reclaim qualification remains the independent proof that the same runtime composition executes with Docker and the production 30-second lease.

Together with the earlier structural contention and real HTTP p95 slices, this satisfies the remaining #125 qualification criteria without changing production behavior, SQLite FULL durability, fencing, admission bounds, lease duration or heartbeat cadence.
