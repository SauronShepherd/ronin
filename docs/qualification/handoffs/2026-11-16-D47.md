## Interpretación técnica para mañana

La evidencia mixta sugiere una frontera sensible a timing entre el consumer
Kafka, el descubrimiento de la segunda partición y la política de parada por
polls idle. No se ha probado aún la causa raíz. En el primer intento, el
servidor no reportó un error: devolvió una respuesta aparentemente correcta
pero incompleta. El reintento confirma que el camino puede drenar 64/64, pero
no demuestra que lo haga de manera determinista.

Puntos de inspección concretos:

1. `python/studio_streaming/runtime.py`, especialmente el bucle
   `KafkaStreamingRuntime.run_until_idle`: cada micro-batch llama a
   `run_once`, que construye y cierra un `KafkaJsonSource` nuevo.
2. `python/studio_streaming/kafka.py`, especialmente `KafkaJsonSource.poll`:
   assignment explícito, `list_topics`, deadline bounded y repetición de
   `consumer.consume` ante resultados vacíos/EOF.
3. `tests/test_streaming_runtime.py` y `tests/test_streaming_kafka.py`: existe
   una regresión de poll vacío seguido por registros de la partición 1, pero
   falta un test que modele la secuencia completa de supervisor: partición 0
   drenada, varios polls vacíos y partición 1 visible antes de aceptar idle.
4. `tools/seed_live_streaming.py`: el fixture `ronin-live-sustained-events`
   tiene 64 registros, 32 por partición; el producer hace `flush(15)` antes de
   registrar las definiciones.

Siguiente implementación razonable, sólo después de reproducir:

- Añadir una regresión determinista que reproduzca `32/64` dentro de
  `run_until_idle`, no sólo dentro de una llamada aislada a `poll`.
- Decidir y documentar el contrato correcto: reusar un consumer durante la
  supervisión, introducir backoff/ventana bounded para descubrimiento de
  particiones, o ajustar la definición de `idle_polls`; conservar siempre
  `max_batches`, `max_records`, los límites de bytes y el checkpoint durable.
- Añadir una prueba negativa que demuestre que un límite agotado no se
  convierte en espera indefinida ni avanza el checkpoint incorrectamente.
- Repetir la campaña live varias veces en el mismo candidato corregido. Sólo
  si todos los intentos exigidos pasan, generar un nuevo candidato, limpiar y
  regenerar, verificar y registrar una celda PASS separada.
- No borrar los dos recibos D47: el primero es la evidencia de FAIL y el
  segundo es una observación PASS de repetición.
