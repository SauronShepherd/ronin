# Govern Studio Proposal

## 1. Purpose

Govern Studio is the local-first Ronin capability for creating synthetic data
fixtures that are reproducible, relationally consistent, inspectable and
exportable. Its product promise is not “safe fake data”. Its promise is a
controlled workflow that makes the assumptions, evidence, limitations and
publication decision explicit.

Ronin remains the host. Govern Studio is a vertical plugin. The implementation
may keep the Python package name `studio_synthetic_data` during the compatibility
period, while the user-facing identity, plugin id, capabilities and APIs use
`govern-studio`.

## 2. Design conclusions after ten review passes

1. A schema is necessary but insufficient: the plan also needs relationships,
   distributions, null behavior, business constraints, privacy posture and
   intended use.
2. A sample is evidence, not truth. Sampling metadata must carry source scope,
   sampling method, row count, time window and sensitivity handling.
3. The agent/orchestrator must never guess facts. Profilers, generators and
   validators are deterministic tools with versioned contracts.
4. Primary and foreign keys must be generated by a relational planner, not by
   independent column generators.
5. Constraints must be executable objects with explicit failure semantics.
6. Validation must be a multidimensional expectation suite, not a single score.
7. Privacy and utility are separate axes. Non-DP generation cannot claim a
   formal privacy guarantee.
8. Every run needs a content-addressed plan, input profile, generator version,
   validation report, output manifest and audit trail.
9. Export formats are providers. CSV/JSONL are baseline; SQLite, Parquet,
   DuckDB and open-table formats must not contaminate the domain core.
10. Publication is a separate state transition requiring policy evaluation and,
    where configured, human approval.

These conclusions are consistent with NIST's warning that synthetic data without
differential privacy does not provide robust protection against privacy attacks,
with JSON Schema 2020-12 as a portable structural contract, with OpenLineage's
job/run/dataset/facet model, and with declarative data-quality Expectations.

## 3. Product scope

### 3.1 In scope

- local schema authoring and import;
- optional CSV, JSONL, SQLite and dataframe sample ingestion;
- metadata profiling without copying sensitive values into logs;
- table graph construction and relationship authoring;
- deterministic baseline generators;
- provider-based statistical generators;
- relational generation with parent-first planning;
- row-level and cross-table constraints;
- quality, utility and risk reports;
- local preview and bounded full generation;
- pluggable exporters;
- run history, artifacts, evidence and audit events;
- UI, REST, CLI and Python SDK adapters;
- safe failure, cancellation, retry and cleanup.

### 3.2 Explicitly out of scope for the first release

- claiming regulatory compliance from a green validation report;
- automatic discovery of every business rule;
- unrestricted LLM-generated executable code;
- cloud warehouse integrations in the API process;
- formal differential privacy unless a separately reviewed provider is installed;
- publishing to external systems without a destination policy and connector;
- silently repairing failed constraints.

## 4. Mental model

```text
Source scope / authored schema
          |
          v
  Govern Studio request
          |
          v
  Immutable generation plan
          |
          +--> profile evidence
          +--> relationship graph
          +--> constraint compilation
          +--> policy preflight
          |
          v
  Generated candidate
          |
          +--> structural validation
          +--> relational validation
          +--> statistical utility evaluation
          +--> privacy-risk indicators
          +--> intended-use gate
          |
          v
  Validated artifact --approval--> publishable artifact --export--> destination
```

The UI can help author a request, but the server-side plan and policy engine are
the authority. A preview is never implicitly publishable.

## 5. Domain model

### 5.1 Core identifiers

```text
GovernanceWorkspaceId
GovernanceRequestId
GenerationPlanId
GenerationRunId
ProfileId
ValidationReportId
ArtifactId
ExporterId
PolicyDecisionId
ApprovalId
```

All identifiers are opaque, stable and non-sensitive. Use UUIDv7 where time
ordering is useful; never encode a source URL, user email, secret or raw value in
an id.

### 5.2 Generation plan

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "schema_version": "govern-studio.plan/v1",
  "plan_id": "plan_01...",
  "workspace_id": "ws_01...",
  "intended_use": "local_integration_tests",
  "privacy_posture": "non_dp_local_fixture",
  "seed": 42,
  "tables": [],
  "relationships": [],
  "constraints": [],
  "expectations": [],
  "generation": {
    "row_counts": {"customers": 1000},
    "scale_mode": "absolute",
    "provider": "builtin.baseline/v1"
  },
  "export": {
    "format": "sqlite",
    "destination": "artifact://local/fixtures.db"
  }
}
```

Structural JSON Schema validates shape. Domain validation additionally checks
graph references, key compatibility, provider capabilities, size limits,
destination policy, seed rules, and version compatibility.

### 5.3 Table and column semantics

Each table declares a stable logical name, row strategy, columns, primary key,
indexes and optional source profile reference. Each column declares:

- logical type and physical export type;
- nullable and target null rate;
- generator provider and provider configuration;
- min/max, precision, scale, format and timezone where relevant;
- categorical support and weights;
- sensitivity class (`public`, `internal`, `personal`, `special`, `unknown`);
- deterministic derivation expression if it is not sampled;
- whether values may be reused across tables;
- expectation overrides.

### 5.4 Relationships

The graph supports one-to-one, one-to-many, many-to-many through a bridge table,
optional foreign keys, composite keys, self-reference, and acyclic generation
groups. Each edge declares cardinality, nullability, orphan policy and the
parent key mapping. Cycles require a two-phase strategy: allocate identifiers,
then resolve references, then validate.

### 5.5 Constraints

The first constraint vocabulary:

```text
range(column, min, max)
inequality(low_column, high_column, inclusive)
conditional_null(condition, column, null_rate)
conditional_value(condition, column, allowed_values)
regex(column, pattern)
date_order(start, end)
foreign_key(child, parent)
cardinality(parent, child, distribution)
aggregate(child, group_by, measure, operator, target)
mutual_exclusion(columns)
functional_dependency(determinant, dependent)
```

Every constraint has `constraint_id`, `severity`, `scope`, `enforcement_mode`,
`evidence`, `version` and `on_violation`. `on_violation` is one of
`fail`, `reject_row`, `repair`, `warn`. `repair` is forbidden for sensitive
outputs unless a policy explicitly allows it and the repair count is recorded.

## 6. Profiling architecture

The profiler is a streaming, bounded, privacy-aware service. It must not retain
raw samples by default.

### 6.1 Profile outputs

For every table:

- row count and approximate size;
- observed columns and inferred logical types;
- null count/rate;
- distinct estimate and exact distinct for bounded domains;
- numeric min, max, mean, quantiles and histogram bins;
- categorical top-k frequencies plus “other”;
- date range, granularity and seasonality hints;
- candidate primary keys;
- candidate foreign keys with overlap and confidence;
- duplicate row rate;
- sensitive-data detector findings as warnings, never as a proof of absence.

For every profile, record the algorithm version, sample size, sampling method,
source fingerprint, redaction policy and expiration. A source fingerprint is a
hash of metadata and bounded statistics, not raw data.

### 6.2 Relationship detection

Candidate FK scoring should combine:

```text
score = 0.30 name_similarity
      + 0.25 type_compatibility
      + 0.25 child_to_parent_overlap
      + 0.10 parent_uniqueness
      + 0.10 nullability/cardinality_fit
```

The score only suggests a relationship. It cannot activate a relationship in a
plan without user confirmation or a trusted catalog constraint.

### 6.3 Sensitive data handling

Default profile output stores categories, counts and numeric summaries, not raw
values. High-risk columns are sampled only with explicit opt-in. Logs redact
values, paths, tokens and connection strings. Profile artifacts have retention
and deletion metadata.

## 7. Generation engine

### 7.1 Provider contracts

```python
class ColumnGenerator(Protocol):
    provider_id: str
    version: str
    def fit(self, profile: ColumnProfile, config: Mapping[str, object]) -> None: ...
    def generate(self, request: GenerateColumnRequest) -> Iterator[object]: ...

class RelationalPlanner(Protocol):
    def compile(self, plan: GenerationPlan) -> ExecutionGraph: ...

class ConstraintExecutor(Protocol):
    def enforce(self, batch: RowBatch, constraint: Constraint) -> ConstraintResult: ...
```

Providers are discovered through `ronin.generators.v1`, validated by manifest,
and isolated when they execute untrusted or heavyweight code.

### 7.2 Built-in providers

Baseline providers are deterministic and dependency-free:

- sequential integer/UUID keys;
- weighted categorical values;
- bounded integer/float;
- date and timestamp windows;
- boolean with probability;
- email/slug/identifier placeholders;
- null injector;
- derived column expression;
- parent-key sampler.

Optional providers can use Faker-like custom providers, copulas, statistical
models or differential privacy. Their package, license, seed behavior, privacy
claim and resource requirements must be declared.

### 7.3 Seed model

Derive sub-seeds rather than sharing one mutable RNG:

```text
seed(table_name, column_name, batch_number, provider_id, plan_fingerprint)
```

This allows parallel generation while preserving reproducibility. The plan must
declare whether reproducibility is expected across engine versions; by default
it is guaranteed only for the exact provider and engine versions recorded in the
run.

### 7.4 Relational execution

1. Validate all references and build a graph.
2. Topologically order tables where possible.
3. Allocate parent primary keys.
4. Fit and generate parent columns.
5. Materialize child FK pools from parent keys.
6. Generate child rows and cardinalities.
7. Resolve cycles in a declared second phase.
8. Apply constraints in deterministic order.
9. Validate each batch before committing it to staging.
10. Commit an immutable artifact manifest only after all tables pass.

Never generate child foreign keys as unrelated random values when an active
relationship exists.

## 8. Validation and utility

### 8.1 Expectation suite

Each expectation has:

```json
{
  "expectation_id": "expect_01",
  "kind": "column_null_rate",
  "target": {"table": "customers", "column": "email"},
  "threshold": {"min": 0.05, "max": 0.15},
  "severity": "error",
  "sampling": "full",
  "version": 1
}
```

The report stores observed value, threshold, pass/fail/skip, execution duration,
evidence reference and diagnostic details. A skipped check is never a pass.

### 8.2 Required validation dimensions

```text
schema            columns, logical types, nullability
volume            row counts and size bounds
missingness       null rates and conditional nulls
uniqueness        PKs, candidate keys and duplicate rows
integrity         FK existence, cycles and cardinality
distribution      quantiles, histograms and categorical frequencies
relationships     correlations and cross-table counts
business_rules    executable constraints
privacy_risk      exact/near matches and rare-combination warnings
operability       export readability, partitioning and performance
```

### 8.3 Utility score

Do not expose one universal score as a truth claim. Show dimension scores plus a
use-case disposition:

```text
fitness = pass(required_expectations)
       AND pass(policy_gate)
       AND no_unacknowledged_critical_warning
```

Optional aggregate scores are labeled as decision aids and must include weights,
sample sizes and confidence intervals.

### 8.4 Privacy assessment

Baseline Govern Studio reports indicators only:

- exact row overlap when a permitted comparison is available;
- nearest-neighbor distance on approved quasi-identifiers;
- rare-combination counts;
- uniqueness amplification;
- direct identifier leakage checks;
- memorization/proximity warnings.

Only a provider with a reviewed formal DP implementation may emit a DP claim,
including epsilon, delta, mechanism, accountant, privacy unit, clipping and
composition history. “Synthetic” alone never emits that claim.

## 9. Governance state machine

```text
DRAFT
  -> PROFILED
  -> PLANNED
  -> GENERATED
  -> VALIDATED
  -> APPROVED
  -> PUBLISHED

Any state -> FAILED
GENERATED -> SUPERSEDED
APPROVED -> REVOKED
```

Transitions are commands, not field edits. Each command checks actor, workspace,
plan version, policy decision and idempotency key. Publication consumes only an
approved immutable artifact. Re-running generation creates a new run and cannot
mutate a published artifact.

## 10. Artifact and evidence model

Artifacts are content-addressed and immutable:

```text
artifact manifest
  artifact_id
  plan_fingerprint
  generator_lock
  source_profile_ids
  validation_report_ids
  table manifests
  exporter id/version
  row counts and byte sizes
  checksums
  created_at / expires_at
  intended_use
  privacy posture and claims
```

Evidence is append-only. A run receipt should reconstruct request, plan,
profile, generated outputs, validations, policy decisions, approvals, exporter,
errors, resource usage and cleanup outcome. Use OpenLineage-compatible input,
output, schema and quality facets where a lineage sink is enabled.

## 11. Exporter architecture

### 11.1 Two provider families

Govern Studio distinguishes file serializers from table-format providers:

| Family | Formats | Contract |
|---|---|---|
| Row/file serializers | CSV, JSON, JSONL, XML | bounded files plus schema sidecar |
| Table formats | Delta, Iceberg, Hudi | metadata, snapshots, schema evolution and commit verification |

CSV, JSON, JSONL and XML are portable exchange formats and do not provide table
history or ACID semantics by themselves. JSONL must be UTF-8 and line-delimited.
XML requires a declared row element, namespace policy and safe scalar conversion;
external entities and entity expansion are disabled.

Delta, Iceberg and Hudi are optional table-format plugins. They must not be
implemented as “write Parquet and rename the directory”: each provider owns its
protocol version, catalog/location semantics, schema mapping, partition policy,
commit protocol, snapshot/history behavior, cleanup and compatibility matrix.

```json
{
  "format_id": "iceberg",
  "family": "table",
  "version": "1.0",
  "protocol_versions": [1, 2, 3],
  "data_file_formats": ["parquet"],
  "features": ["snapshots", "schema_evolution", "time_travel"],
  "catalogs": ["filesystem", "sqlite", "rest"],
  "requires": ["pyarrow"],
  "write_atomicity": "optimistic_commit"
}
```

Exporter providers implement:

```python
class TableExporter(Protocol):
    format_id: str
    version: str
    capabilities: frozenset[str]
    def validate_destination(self, destination: Destination) -> None: ...
    def write(self, artifact: Artifact, destination: Destination) -> ExportReceipt: ...
    def verify(self, receipt: ExportReceipt) -> VerificationReport: ...
```

Baseline order:

1. JSONL, JSON, CSV and XML for portability;
2. SQLite for local application tests;
3. DuckDB database and Parquet directory;
4. Delta, Iceberg and Hudi adapters behind optional extras.

Every exporter must preserve schema, nulls, key types and deterministic ordering
where the target format allows it. File serializers write a manifest and schema
sidecar. Table providers write to run-scoped staging, verify table metadata and
commit a new snapshot/version atomically or report `partial`.

## 12. UI proposal

Govern Studio should expose six steps:

1. **Scope** — choose schema source, sample, intended use and retention.
2. **Model** — inspect tables, types, keys and relationship graph.
3. **Rules** — author constraints and expectations with severity.
4. **Generate** — choose scale, providers, seed and resource limits.
5. **Validate** — review dimension reports, warnings and claims.
6. **Export** — choose format/destination and request approval if required.

The right rail always shows plan version, state, evidence completeness, warnings,
privacy posture and intended-use label. Destructive or external publication
actions require a confirmation dialog showing exact destination and artifact id.

## 13. Security model

- workspace isolation is enforced server-side;
- source reads require explicit data permission;
- sample contents never enter telemetry;
- export destinations are allowlisted;
- provider packages are pinned, scanned and optionally isolated;
- resource limits cover rows, bytes, CPU, memory, wall time and output count;
- cancellation is cooperative and staging cleanup is mandatory;
- secrets resolve through Ronin's secret port and are never persisted in plans;
- policy denial is fail-closed;
- generated artifacts inherit sensitivity and retention metadata.

## 14. Failure taxonomy

```text
invalid_plan
profile_unavailable
profile_expired
relationship_ambiguous
provider_not_found
provider_incompatible
constraint_unsatisfied
resource_limit_exceeded
validation_failed
policy_denied
approval_required
export_destination_invalid
export_verification_failed
lease_lost
cancelled
cleanup_failed
```

Errors must be stable, actionable and safe to display. A retry is allowed only
when the operation is idempotent or run-scoped staging guarantees no duplicate
published output.

## 15. Extension boundaries

```text
Core: plan model, state machine, hashing, ports, policy decisions, evidence
Plugin: profiling, generation orchestration, validation suite, UI/API
Provider: generator, profiler, validator, exporter
Adapter: SQLite, DuckDB, Parquet, open tables, object store
Worker: heavyweight/statistical/DP/untrusted execution
```

No extension may import another plugin's private tables or mutate its state.
Provider registration is declarative and versioned. Hooks are for local
contribution; jobs are for durable work; events are for asynchronous reaction.

## 16. Recommended implementation sequence

Build the deterministic baseline and evidence model before adding statistical or
LLM-based generation. Add one external exporter and one external provider using
only public SDK contracts before declaring the extension architecture proven.
